AI Playbook for product design

A repository for AI prototyping of product scenarios with design system components.
My role
I designed the Playbook concept and architecture: the flow model, screen and specification structure, agent rules, change boundaries, and the working prototype itself.
Format
A React repository with a predefined project structure, AI agent rules, and a design system connected through MCP.
Facts
React + TypeScript · design system via MCP · screen/spec model · working beta prototype in a few days.
Result
Not a static mockup, but a working sequence of screens inside a repository that can be developed and edited further together with an AI agent.
I wanted to test whether a code AI agent could be used not only for isolated interface changes, but for assembling an entire user scenario. For that, I designed a React repository where the project structure, design system, and agent rules are already defined. The output is a working flow made of connected screens built with design system components. It lives in the repository and becomes a basis for further iterations with an AI agent. For precise interface edits and manual adjustments to individual elements, Retune is used, so the whole scenario does not have to be regenerated from scratch. For me, this was more than an interface generation experiment. Playbook became a first step toward a more controllable AI-assisted discovery process, where an agent gradually receives task context, designs a scenario, and assembles a solution in a form that is still useful for further work. The result remains readable and editable for humans while also preserving the structure, specifications, and context needed for future AI-agent iterations. The same artifact can become a continuation point both for a product team and for agent-driven development.
The core idea of Playbook is to give the agent a managed environment instead of an empty project: scenario structure, ready-made components, screen specifications, and clear change boundaries.

The repository gives the agent an environment to work in

Playbook separates the project into a stable foundation and the area where a specific product scenario evolves. Shell, navigation, and the flow engine stay part of the tool itself, while new interfaces are created inside separate flows. The agent does not need to rediscover the whole project every time. The README captures the main rules and constraints, and separate skills were added for more modern code agents to explain how to work with different task types. This helps the agent understand context faster and change the right part of the scenario without touching the rest of the system.

Each screen stores both interface and intent

I connected every screen with a specification: next to screen.tsx there is a spec.ts file describing the screen’s purpose, logic, and states. The specification is displayed directly inside Playbook and remains next to the implementation. On the next iteration, the agent sees not only the existing code, but also why the screen exists, what role it plays in the flow, and which states it needs to support. This is especially important for a multi-step discovery process: the result of the previous step becomes context for the next one, and the meaning of the solution is not lost between iterations.

Constraints became part of the architecture

By default, the agent works in limited mode: it can change the current flow, its screens, and specifications, but does not rebuild Playbook itself. Shell, the flow engine, and root settings remain stable unless the user explicitly asks for a structural change. I captured these constraints not only in the agent rules, but also in the repository architecture: stable infrastructure is separated from the area where the agent can create and change a product scenario. This makes the agent’s work more predictable and reduces the risk that a local task unexpectedly turns into a full application rewrite. For an automated process, this is essential: the agent’s boundaries should be defined not only by instructions, but by the environment itself.

A template became a prototype for an AI-native process

I assembled the working beta in a few days and used it to generate multi-screen product scenarios with real design system components. The experiment showed that simply giving the agent a component library is not enough. It needs a scenario model, context for every screen, and clear boundaries for changes. In practice, Playbook is a starting point for a multi-step discovery process. One stage forms the scenario and interface, and the next receives that result as input and develops the solution further. The next level of this idea is to connect such steps into a single multi-agent process that can support product creation end to end: from problem framing and scenario research in discovery to implementation and preparing the solution for delivery.
